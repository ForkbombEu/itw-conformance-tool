## What was already fixed at `2ba1383` vs what this commit fixes

**Already fixed at `2ba1383`:**

- `finalizeEvidence` already downgraded `pass` to `inconclusive` when `ArtifactStore.finalize` returned limitations. At that HEAD those limitations came only from publication failures: unsafe ID, missing, oversize or unreadable.
- The manager could not restore `pass` on any path I could reach at that HEAD:
  - `withLifecycle` recomputes only when the status changes or extra limitations exist.
  - Each recompute uses a non-`completed` status (cancelled, timed_out, or error for an unknown worker status and for recovery).
  - `summarizeWithLimitations` never returns `pass` for a non-`completed` status.
- The tests for this are kept as regressions.

**Remaining defects, fixed here:**

1. **The decision was keyed on human strings.** The downgrade relied on `limitations.length > 0`, and the publisher had no typed outcome.
   - Fix: `ArtifactStore.finalize` now returns `PublicationOutcome { entries, failures, limitations }`.
   - `failures` is a typed list `PublicationFailure { artifactId, filename, reason }`, with `reason` one of `missing | oversize | unreadable | unsafe_id | write_failed`.
   - Only these typed failures drive the downgrade, through a single function, `applyEvidenceCompleteness` in `summarize.ts`. It changes only `pass` to `inconclusive`. It keeps `fail`, `partial`, `not_tested` and `inconclusive`, and it never touches native verdicts.
   - Informational limitations (such as an unknown source revision) never reach it.
2. **The manager had no evidence-completeness input.** `ExecutionEvidence` now has `publicationFailures?: readonly PublicationFailure[]`. This is an internal aggregation input and is never serialized; `RunnerResult` v1.0 and its strict schema are unchanged.
   - `withLifecycle` applies `applyEvidenceCompleteness` **after** any lifecycle or native recompute. This covers the normal completed path, unknown worker status, cancel, deadline and shutdown.
   - So no recompute can turn a publication failure back into `pass`, even when a publisher has not already downgraded.
   - Cancel or deadline with partial PASS assertions stays `partial`. Artifacts that did publish are kept, and the limitation is added.
   - Recovery of a stranded record that has a stored result is forced to `error`, which can never recompute to `pass` (commented in code).
3. **An exception from the publication path lost all native data.** Reproduced through the real server (see below): a real `EACCES` on the artifact root made `finalize` throw. The run then became `execution.status = error` with `Infrastructure error: …`, 0 assertions and `not_tested`, and the private state path leaked into `execution.error`.
   - Fix, per file: mkdir, copy and rename errors become a typed `write_failed`. The temp file is cleaned up.
   - If the manifest write fails, none of the new copies is advertised; each is reported as `write_failed` and removed.
   - `finalizeEvidence` also catches any exception from the store, for example an unsafe run ID. It keeps the native result and returns `artifacts: []`, a `write_failed` failure for each declared artifact, and a limitation with absolute paths redacted.
4. **Narrow, named internal test-only seam:** `ArtifactStoreOptions.readSource` (an `ArtifactSourceReader`), passed through as `ServeRunnerOptions.artifactSourceReader`. It replaces only the source-file read during initial publication; production reads the real filesystem.

Already-stored results are not rewritten when bytes are later deleted or tampered with. The existing download integrity behaviour (`ARTIFACT_CORRUPT` 500 / `ARTIFACT_MISSING` 410) is unchanged and its tests still pass.

   - a schema-valid result with `completed`, native suite `PASSED` and every assertion `PASS`;
   - `summary.result = inconclusive` with 0 native failures;
   - `artifacts: []` and the limitations "could not be read" and "could not be published";
   - HTTP 404 for `/artifacts/native-results`;
   - no private path in the raw JSON.

   After `close()` and a restart on the same state root **without** the seam, the result is deep-equal. A same-key POST returns 200 with the same `run_id`, the result bytes are identical, and the artifact is still 404.

3. A real read-only artifact root (`chmod 0500`, no seam) gives `completed` with no `execution.error`, all native assertions PASS, `inconclusive`, `artifacts: []`, the limitation "could not be stored", and 404.

## Remaining limitations

- Live SUT acceptance: **NOT RUN**.
- The compiled `dist/main.js serve-runner` path (production-composition section B) was re-run only for the successful publication path. An R17 failure through the compiled binary is NOT RUN, because it cannot be injected without a seam in the shipped CLI.
- `publicationFailures` is not persisted in the run record. It is not needed after finalization: a stored terminal result already carries the downgraded summary and the limitation, terminal results are never recomputed, and recovery of a stranded record forces `error`, which cannot recompute to `pass`.
- The oversize limitation no longer prints the file's byte size; the typed failure does not carry it.
- The certificate test flake is pre-existing and untouched.
