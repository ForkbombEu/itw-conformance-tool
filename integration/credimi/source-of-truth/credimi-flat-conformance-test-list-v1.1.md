# Credimi Flat Conformance Test List v1.1

This is a flat, test-authoring-oriented list extracted from the EUDI legal/ARF/WE BUILD/ETSI evidence work done so far.

It is **not** an official conformance suite and not a certification scheme. It is a practical inventory of tests that can be implemented as Maestro Wallet automation, StepCI protocol/API tests, trust-helper checks, external OpenID / WE BUILD / ETSI / QTSP integrations, or manual/CAB-style assurance review.

## Source scope note

This v1.1 file uses the EUDI-targeted source scope defined in `credimi-conformance-source-scope-v1.1.yaml`.

Included from the OpenID Conformance Suite spec-link catalogue: OID4VCI, OID4VP, HAIP/HAIPA, SD-JWT, SD-JWT VC, OAuth Status List, OpenID Federation, and ISO 18013-7 as reference-only.

OAuth/OIDC dependencies such as PKCE, PAR, JAR, JARM, DPoP, JWT/JWK/JWA, OAuth AS Metadata and OIDC Discovery are included only when directly used by a concrete EUDI-targeted test.

Excluded for now: FAPI, CIBA, Open Banking/regional profiles, CAEP, RISC, Shared Signals, AuthZEN and other non-EUDI profiles.

## Evidence classification

| Classification                | Meaning                                                                                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **definitive evidence**       | The test directly proves the observable claim being made. Example: a Wallet successfully completes a PID SD-JWT issuance flow using a credential offer whose metadata was recorded in Temporal.                                             |
| **conditional evidence**      | The test strongly suggests the claim, but the internal implementation is not directly observed. It can often be strengthened by chaining another test, usually presentation/verification or a negative fixture.                             |
| **requires external testing** | Credimi black-box automation is not enough. The test requires a headless conformance suite, verifier-side cryptographic inspection, source/instrumentation, QTSP service, qualified validation service, lab/CAB review, or manual evidence. |

## Correction to the examples

Your examples are basically right. The only thing I would sharpen is the wording of “verify”.

| Example                                           | Classification           | Correction                                                                                                                                                                                                    |
| ------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wallet can receive a PID SD-JWT                   | **definitive evidence**  | Yes, if `credential_metadata` records PID + SD-JWT and Maestro succeeds. This proves observable issuance interoperability for that profile.                                                                   |
| Wallet can receive an SD-JWT signed with RSA-2048 | **definitive evidence**  | Yes, for completing issuance under that recorded metadata profile.                                                                                                                                            |
| Wallet can verify an SD-JWT signed with RSA-2048  | **conditional evidence** | Correct. Issuance success alone does not prove signature verification. A later presentation flow strengthens the evidence; an invalid-signature negative fixture is needed for definitive rejection evidence. |
| Wallet can store an SD-JWT signed with RSA-2048   | **conditional evidence** | Correct. Presentation after issuance is strong black-box evidence that it was stored/retrievable. Internal storage format/security remains external/manual/certification evidence.                            |

## How this maps to `credential_metadata`

The new `credential_metadata` artifact lets Credimi unroll broad flows into profile-specific tests.

Useful metadata dimensions:

- credential profile: PID, EAA, QEAA/QEEA;
- format: SD-JWT, mdoc, W3C VC JWT, W3C VC Data Integrity, etc.;
- grant type: authorization code, pre-authorized code;
- issuer binding: X.509/x5c, JWK, DID, trusted-list entry;
- signing algorithm: RSA-2048/RS256/PS256, ES256, EdDSA, etc.;
- revocation/status mechanism;
- proof type / key binding method;
- issuer metadata hash;
- fetched-at timestamp;
- credential configuration ID;
- trust mode: production, pilot, sandbox, mock.

A successful Maestro action can then be interpreted as:

> The Wallet completed an issuance/presentation flow for the exact metadata profile recorded in Temporal.

But for cryptographic verification claims, use the stricter rule:

> Positive flow success is conditional. Negative fixtures and verifier-side/headless inspection are required for definitive crypto rejection/validation evidence.

## Minimal next implementation step

Add a `conformance_context.credential_metadata` object to the Maestro step input.

Recommended shape:

```json
{
  "parameters": {
    "deeplink": "openid-credential-offer://..."
  },
  "conformance_context": {
    "credential_metadata": {
      "credential_issuer": "https://issuer.example",
      "credential_configuration_ids": ["pid_sd_jwt"],
      "credential_profile": "PID",
      "credential_format": "SD-JWT",
      "grant_types": ["authorization_code"],
      "issuer_binding": "x5c",
      "signing_algorithms": ["RS256"],
      "key_size": "RSA-2048",
      "issuer_metadata_url": "https://issuer.example/.well-known/openid-credential-issuer",
      "issuer_metadata_sha256": "...",
      "fetched_at": "2026-05-20T00:00:00Z",
      "trust_mode": "sandbox"
    }
  }
}
```

This one change makes many of the tests above reportable without changing Maestro itself.
